Game feel

A good game answers instantly, shows clearly what just happened and stays fun to repeat. These are the details I work on.

100 msSpace
300 ms · feels lateSpace

Response and input delay

  • Show a response within 100 ms, or it feels laggy.
  • Players need about 240 ms to see, decide and act, so enemy warnings last longer.
  • Coyote time (0.10–0.15 s) and a jump buffer (0.08–0.20 s) forgive a press that is a bit late or early.
Rigid
Squash and stretch

Disney's animation principles

  • Squash and stretch shows weight: stretch on the jump, squash on landing, same volume.
  • Anticipation for enemies, almost none for the player: a wind-up never delays the action.
  • Arcs, easing and follow-through make motion feel alive.
  • Exaggerate only rare moves; routine ones stay short and light.
Hit stop 100 ms · flash 80 ms · shake 0.24 s

Feedback timings

Hit stop
50–100 ms (3–6 frames), never past ~8 frames on a player action
White flash
50–100 ms: shorter is invisible, longer smears
Screen shake
0.1–0.3 s, from a decaying "trauma" value, squared
UI tween
0.10–0.25 s, ease-out by default
Landing squash
80–150 ms, scaled by impact speed
None
Balanced
Too much

Juice, in balance

  • In a study of 3,018 players (Kao, 2020), no juice and too much juice both did worse than a medium-high amount.
  • One event, one peak: sound, particles, camera and UI hit together.
  • Small for routine, big for rare, so rare moments stand out.
ColourLightness only
HSL OKLCH

Colour and readability

  • Colour carries meaning: player, hazards and goals stand out by contrast and silhouette.
  • Palettes in OKLCH: same lightness, evenly spaced hues, so no colour shouts. This site uses it.
  • An effect never covers what it announces.
Screen shake: 100%50%Off

Comfort and accessibility

  • At most 3 flashes a second, and no saturated red flashing.
  • Sliders, not toggles, for screen shake and full-screen effects.
  • Input keeps working through any freeze, so no press is lost.

Why it feels good

Each hit, one step higher

Sounds that climb

  • A coin chain that goes one step higher per pickup is a progress bar you hear. The brain predicts the next step and enjoys it landing: dopamine follows anticipation.
  • The same sound on repeat fades from attention (habituation). A rising or slightly random pitch keeps it fresh.
  • A surprise lands harder than an expected reward, so a rare big hit beats a big hit every time.
Same press, two answers
A ? Silent
A +1 Answered

Every action answered

  • The "I did that" feeling (sense of agency) is strongest when the result is instant and matches the action.
  • Players come back for competence, proof they are getting good (Ryan, Rigby and Przybylski, 2006).
  • Silence reads as "did it work?". Sound, image and vibration together read as one solid event.
Staying in the channel

Flow

  • Flow (Csikszentmihalyi) needs clear goals, instant feedback and a challenge just above your skill.
  • Too easy turns into boredom, too hard into anxiety, so the challenge grows with the player.
  • Feedback lets players correct in the moment and stay in the channel.
Faster near the goal

The pull of the finish

  • People speed up near a goal: in a coffee card study, customers bought faster as a free drink got close (Kivetz, Urminsky and Zheng, 2006).
  • So progress stays visible, and the last step gets the biggest moment.
  • A clear "done" signal closes the loop and feels like a reward.

What I aim for in my games

  1. Respond on the first frame. Squash sells the wind-up without delaying the move.
  2. Forgive the player. Generous timing windows, so mistakes feel like yours, not the game's.
  3. Clarity before polish. Rule first, then a readable change, then feedback, decoration last.
  4. Fun to repeat. Small feedback for what you do a hundred times, a big moment for what you do once.
  5. Tune in data, not code. Timings live in one place, so I adjust the feel while playing.

In Magic Sort: a tube dips when picked, shakes on a wrong move, pours along an arc and bounces when full. Levels slide in tube by tube so you can read the board first, and all timings live in one ScriptableObject.

Building games with Claude Code

I use Claude Code as a well-briefed teammate, set up like a project: its own agents, skills, rules and safety hooks. The design, the shipped code and the final call stay with me.

  • 9 agents
  • 22 skills
  • 2 rules
  • 1 safety hook
  • 3 models, each where it fits

Agents work in parallel, I decide. I write the brief, agents dig in together, and nothing goes in until I review it and test it in Unity.

› make the jump feel better ● game-feel skill stretch Y 1.2 90 ms squash Y 0.8 120 ms coyote 0.12 s · buffer 0.15 s ● Edit Scenes/Level1.unity ✕ guard-unity-yaml: blocked The open editor would overwrite this scene. Change it in Unity. › ok, I'll set it in the editor

Skills give numbers, hooks set limits. A skill turns a vague wish into values, and a hook stops an edit that would break an open scene.

Every change starts with an agent finding its Linear issue, so nothing gets built twice. The grill-me skill questions the plan with me first. Claude writes the shortest diff in the right place, read-only reviewers check it in parallel and Claude reads the compile log. The last step is mine: I test it in Play Mode.

Assets from scripts, not by hand

The character, rig, animations, props and level kit are built by Python scripts in headless Blender. Claude edits the script, Blender exports the FBX, and Unity rebuilds the prefabs, materials and animator. A palette check fails the build if signal colours clash, colour-blind vision included. Generated files are never edited by hand.
